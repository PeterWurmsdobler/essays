Productivity in Software Development using AI Models --- A Pilot Project

My experience of using Microsoft Copilot on a small pilot project led me to appreciate a new way of software development.

The development in machine Learning (ML) & Artificial Intelligence (AI) over the past decades has been astounding and I had some exposure during my professional life: academic research on simple Artificial Neural networks (ANNs) in the late 1980s, Fuzzy Logic to solve control system problems in the 1990s, and Convolutional Neural Networks (CNNs) for autonomous vehicle perception tasks in the 2010s. Today, Large Language Models (LLMs) based on Generative Pre-trained Transformers (GPT) are ubiquitous and have invaded our everyday life, privately and professionally. Therefore, I was very much interested in trying out Microsoft Copilot [1] for developing software in a small pilot project in order to familiarise myself with a new mode of developing software; in this post I would like to share my experience thus far.

A Sandbox Project

After a few decades of attempting to play the piano, I still find it hard to read sheet music; I have been wondering for a while a) what are the impediments that make reading sheet music so hard, and b) what could be done to assist in this mental task. My considerations are explained in a story preceding this one:

In order to actually mitigate the issues, I joined a Forum [2] and discussed what could be done to Facilitate reading sheet music [3]. Apart from reading ‘practice, practice, practice’ as a solution to my sheet music reading inability, the members’ recommendation was to write a so-called ‘plugin’ for the well-established music notation software MuseScore [4]: a combination of Qt [5] Meta-object Language (QML) and JavaScript. While I do have experience with Qt as a C++ library, I have never used QML nor do I know much JavaScript. So how do I go about writing a Musescore plugin?

For any software engineer faced with the task of realising a requirement, the first port of call is to find some representative examples for an implementation, obtain some inspiration and, in the best case, perhaps some working projects (with source code) that could form a basis to work from. Unfortunately, the programming style of most examples was very difficult to follow (monolithic all-in-one file solutions), and I could not really use those as a starting point.

This is where Copilot came in. When asked: ‘Can you write a small MuseScore 4.0 plugin in QML that produces a dialogue with one check box?’ the output was a QML file that looked like some of the examples, and most importantly, once loaded in MuseScore, worked. The generated output is boiler-plate code and it is of course not surprising that an LLM trained on a large code base would be able to produce that. ‘Could you add some more check-boxes’, I continued prompting Copilot, and ‘Please could you make them mutually exclusive?’ Gradually I asked for more features such as nice colour selection boxes, and, as it produced code, I gained some understanding how these features are expressed in JavaScript, i.e. an opportunity to learn the language on the side.

Once the GUI was sorted, I could ask questions like: ‘Could you write a function that goes through all notes in a score, one staff at a time, and then one bar at a time, finally print the note name and tonal pitch code?’ Surely Copilot spat out more code to be copied into my QML plugin. Unfortunately, it did not work first time. Challenged about that, Copilot could find a workaround after I passed on the run-time error messages into a new prompt. Once some simple functions were produced to collect notes or apply certain functions to those notes, I asked if these pieces of functionality could be extracted into separate Javascript files and then imported, i.e. begin structuring the code into components. Copilot came up with suggestions in the correct syntax and it worked. Even nesting Javascript functions and files worked; quite impressive. Note that at that point I had not written a single line of code myself, only instructed Copilot, then copied code into the plugin folder to try it out in Musescore.

Switching AI Gears

Since I have difficulties reading different clefs, I thought that it should be possible to only use one clef class only by offsetting said clef by one or several octaves for every bar as needed, depending on the pitch of all notes in the bar, but at the same time avoid too many changes in clef offsets from one bar to the other. The notes in a bar (note group) are identified by their MIDI numbers from 1to 127; the offset clefs are identified by a clef reference pitch, 71 for the B (middle line in staff) for a standard violin clef. I tried to express that in more abstract terms: 

Suppose I have a list of groups where each group contains random numbers from 1 to 127. I would now like to assign a reference number to each group where the reference number is one of the following list: 23, 35, 47, 59, 71, 83, 95, 107, 119. The assignment should optimise the criteria:
- the sum of all distances of all notes to the respective reference number should be minimised
- the change in reference number from one group to the next group in the sequence should be minimised.
Cann you implement a solution in Javascript?

Copilot thought for a bit, then responded within a few seconds: 

To solve this problem, you can use a dynamic programming approach. Here's the plan:
1. **Define the Problem**:
   - You have a list of groups, where each group contains random numbers (notes).
   - You need to assign a reference number to each group from the given list of reference numbers.
   - The goal is to minimize:
      - The sum of distances between the notes in each group and the assigned reference number.
      - The change in reference number between consecutive groups.
2. **Dynamic Programming Approach**:
   - Use a 2D table `dp[groupIndex][referenceIndex]` to store the minimum cost for assigning a reference number to a group.
   - For each group, calculate the cost of assigning each reference number, considering both the distance of notes to the reference number and the change in reference number from the previous group.
   - Transition between states by iterating over all possible reference numbers for the current and previous groups.
3. **Steps**:
   - Initialize the `dp` table for the first group.
   - Iterate through all groups and calculate the cost for each reference number.
   - Track the minimum cost and the reference number assignments.

### Explanation:
1. **`calculateDistanceSum`**: Computes the sum of distances between notes in a group and a reference number.
2. **Dynamic Programming Table (`dp`)**:
   - `dp[i][j]` stores the minimum cost for assigning the `j`th reference number to the `i`th group.
   - `prevRef[i][j]` tracks the reference number index for the previous group that led to the minimum cost.
3. **Backtracking**: After filling the DP table, backtrack to retrieve the sequence of reference numbers that minimizes the cost.
### Output:
The code returns the assigned reference numbers for each group and the minimum cost. This approach ensures both criteria are optimized.

Conclusion

This experience made it clear to me: while I may be able to specify a problem in plain English quite accurately, I may not know the appropriate algorithm, let alone realising it in a new programming language; but the collective of software engineers, past and present, does. Copilot is the embodiment of that collective knowledge as it had ingested an enormous amount of data in its training phase and found a statistical representation in its internal weights; the model implicitly ‘knows’ about a lot that is known to humanity but not to necessarily an individual; I may not know, but others will and by extension Copilot.

During this experiment I have learned that it is easy to produce code (I cannot say write as I have barley written a line myself); one does indeed become very productive. It is however very draining as one has to watch out for hallucinations; at times an output is plain-wrong, or ridiculous, which Copilot would readily admit to. With no software development experience it would be difficult to assess whether the model’s output is useful. With some experience, however, Copilot becomes a power-tool accelerating the software development cycle.
