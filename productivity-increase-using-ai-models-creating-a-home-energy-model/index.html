Productivity Increase using AI Models --- Creating a Home Energy Model

Using Copilot Claude Sonnet to analyse a schema and generate and input configuration into the Home Energy Model

Over the past months I have been using Microsoft Copilot for various projects, both in a professional and a private context. In this post I would like to share my experience of using Copilot in agent mode to analyse the reference implementation of the UK government’s Home Energy Model (HEM), and to create an input configuration file for a specific property — namely our 1930s semi-detached house.

Figure 1. VSCode showing the Home Energy Model schema as well as the conversation with Claude.

Home Energy Model

The Home Energy Model (HEM) is the UK Government’s proposed National Calculation Methodology for assessing the energy performance of dwellings. Sometimes referred to as SAP-11, it is intended to replace the Standard Assessment Procedure (SAP), now at SAP 10.2; both are used to produce the Energy Performance Certificate (EPC) required for selling or renting out a property in the UK. What is most interesting, however, is that the reference implementation is available under an MIT licence.

The first step was of course to git clone the repository into a local folder on my computer (Ubuntu 22.04.2 LTS), open the project in VSCode, study the README.md, follow its instructions to create a virtual Python environment — as is common practice — download a weather file from Climate.OneBuilding.Org (Cambridge, in my case), and finally run the simplest of all calculations using the demo input configuration test/demo_files/core/demo.json: 

python src/hem.py test/demo_files/core/demo.json \
    --epw-file <weather_file>.epw

After a successful run, the folder test/demo_files/core/demo__results contained some files that looked sensible — for instance the demo__results__static.csv with an entry for the ‘Heat transfer coefficient, W/K, 173.915441’. Of course this value is not meaningful, as the input configuration does not represent a real property. At this point I was confident that I had a working HEM at my disposal.

Iterations

My objective was to create an input configuration representative of our 1930s semi-detached house, run a simulation using the Cambridge weather data, and produce the standard output, which should include the property’s heat transfer coefficient as well as an estimated annual energy consumption. The source-code root folder shows src, schema and test folders, but no sign of any documentation describing a process or guideline for creating the input configuration for a specific property — not even concept documents or object-model diagrams. Since I did not fancy reverse-engineering the input schema, I turned to Copilot, using Claude Sonnet 4 — Claude, for short — for an initial analysis:

Can you study the core-input.json schema for the input configuration and the corresponding parser in the source code, and explain how the model is structured?

Claude responded by rephrasing the question, reporting that it had analysed both the schema and the Python program, and then produced a report on its findings. It elaborated on the Building Thermal Model, Zones, Building Elements, Thermal Bridging, HVAC Controls, External Conditions, Internal Gains, and so on. At least I now had a sense of the scope of the model and what it was capable of representing. So I continued:

How would I go about creating an input JSON file for a real property, a semi-detached two-storey, three-bedroom house with gas central heating?

Claude obliged, saying it would help me create an input JSON for exactly such a house. It then analysed the structure of all the demo files, which it had discovered on its own, and after a few minutes produced a written guide, a working example file, and a step-by-step workflow. I studied the generated guides and the example file, but wanted to make sure that a simulation run would actually work:

Can you make sure that the example input file works with the HEM simulation engine and the Cambridge weather data?

It realised that the execution failed but, after several iterations — thanks to the agent mode, using a shell to run the Python scripts and analyse the error messages — Claude fixed the example input file and reported success: the file now ran against the HEM engine, giving a total gas consumption of around 388 kWh and a space-heat demand of about 2.7 kWh/m2 over a one-week (168-hour) period.

At this point I had a working base model. I committed the local changes, then followed the advice to gather the required data for our actual house: building geometry (floor areas, room heights, wall and window dimensions, roof area and pitch, the party-wall area shared with the neighbour); construction details (wall types and U-values, glazing, floor construction, roof insulation, airtightness); the HVAC systems (boiler make and rating, hot-water cylinder, radiators, controls); and occupancy (number of occupants, daily schedules, hot-water usage).

Once I had all the required information gathered in a file specification.txt, more or less in a YAML-like format, I asked Claude to adjust the model accordingly. After a little thought it went off and created a five-step plan, ran the simulation, discovered a few JSON validation and runtime errors, and fixed them until a final model was generated. Among other things it converted the model from two zones to ten rooms — an entrance hall, front room, family room, kitchen/diner, bathroom, two master bedrooms, a box room, plus two unheated zones — each with its own thermostatic radiator valve (TRV) control and its own heating schedule (standard rooms 16–21 °C, bathroom up to 22 °C, bedrooms 15–18 °C).

Claude also discovered a bug in the HEM: two unheated zones create a conflict in an internal dictionary. The workaround is a simple dummy heating with zero output for those rooms. After resolving a few other snags, I wanted to extend the simulation to a full year. Claude upscaled the model, identifying all the elements that needed changing, and produced an input configuration for a whole year using nested, named patterns — extending the run from 168 hours to 8,760, repeating the schedules and TRV controls across all 365 days, and generating a daily shower event. The full-year figures came out at an annual space-heat demand of about 253 kWh/m2, a total gas consumption of roughly 14,800 kWh and some 640 kWh of electricity.

These values were already in the right ballpark. For me it took some further iterations to adjust the parameters, which I did gradually, first by asking questions about the schema, such as:

How would a flat ceiling be modelled that has an unheated roof space above? How does the schema configure an internal wall between two adjacent rooms?

Claude gave very good answers to all of these questions and helped me to understand some of the underlying concepts, so that I could arrive at a decent model.

Conclusion

The workflow presented here is a distilled — and in a sense sanitised — version of a much longer conversation, but the process is clear: ask Claude to analyse the schema (or the source code), then to build a simple model and gradually improve it by adding complexity, while always making sure that the calculation still runs. Copilot — Claude, in my case — in agent mode will use any output errors to detect missing input quantities or inconsistencies and fix them; or, where it cannot fix them, indicate where the issues are, or even discover a bug in the source code.

Beyond the initial objective, the process of building and enhancing an input file allows one to learn the schema and, implicitly, to create a model suited to one’s own case; there is a myriad of possible thermal models for a semi-detached house. What matters is to gauge the output — to verify that the model converges and that the predicted thermal losses or energy consumed correlate with the recorded data, such as the annual energy bill. It is the desired outcome that drives the cooperation with Claude.
