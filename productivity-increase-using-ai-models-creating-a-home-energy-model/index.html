Productivity Increase using AI Models --- Creating a Home Energy Model

Using Copilot Claude Sonnet to analyse a schema and generate and input configuration into the Home Energy Model

Over the past months I have been using Microsoft Copilot [1] for various projects, both in a professional and a private context. In this post I would like to share my experience of using Copilot in agent mode to analyse the reference implementation [2] of the UK government’s Home Energy Model [3] (HEM), and to create an input configuration file for a specific property — namely our 1930s semi-detached house.

Figure 1. VSCode showing the Home Energy Model schema as well as the conversation with Claude.

Home Energy Model

The Home Energy Model (HEM) is the UK Government’s proposed National Calculation Methodology for assessing the energy performance of dwellings. Sometimes referred to as SAP-11, it is intended to replace the Standard Assessment Procedure (SAP) [4], now at SAP 10.2 [5]; both are used to produce the Energy Performance Certificate [6] (EPC) required for selling or renting out a property in the UK. What is most interesting, however, is that the reference implementation [2] is available under an MIT licence [7].

The first step was of course to git clone the repository into a local folder on my computer (Ubuntu 22.04.2 LTS), open the project in VSCode [8], study the README.md, follow its instructions to create a virtual Python environment — as is common practice — download a weather file from Climate.OneBuilding.Org [9] (Cambridge, in my case), and finally run the simplest of all calculations using the demo input configuration test/demo_files/core/demo.json: 

python src/hem.py test/demo_files/core/demo.json \
    --epw-file $HOME/Downloads/GBR_ENG_Cambridge.AP.035715_TMYx.2004-2018.epw

After a successful run, the folder test/demo_files/core/demo__results contained some files that looked sensible — for instance the demo__results__static.csv with an entry for the ‘Heat transfer coefficient, W/K, 173.915441’. Of course this value is not meaningful, as the input configuration does not represent a real property. At this point I was confident that I had a working HEM at my disposal.

Iterations

My objective was to create an input configuration representative of our 1930s semi-detached house, run a simulation using the Cambridge weather data, and produce the standard output, which should include the property’s heat transfer coefficient as well as an estimated annual energy consumption. The source-code root folder shows src, schema and test folders, but no sign of any documentation describing a process or guideline for creating the input configuration for a specific property — not even concept documents or object-model diagrams. Since I did not fancy reverse-engineering the input schema, I turned to Copilot, using Claude Sonnet 4 — Claude, for short — for an initial analysis: 

> Can you study the core-input.json schema for the input file for the src/hem.py programme and summarise the key concepts in the input please?

Claude responded by rephrasing the question, reporting that it had analysed both the schema and the Python program, and then produced a report on its findings (showing the first few lines): 

GitHub Copilot: Now I have a comprehensive understanding of the core-input.json schema. Let me provide you with a detailed summary of the key concepts.
## Summary of Key Concepts in the HEM Core Input Schema
Based on my analysis of the core-input.json schema for the Home Energy Model (src/hem.py), here are the key concepts organized by domain:
### **Core Required Components**
The schema defines 12 mandatory top-level sections that every input must contain:
1. **ColdWaterSource** - Cold water temperature profiles
2. **Control** - Various control systems (timers, setpoints, cost optimization)
3. **EnergySupply** - Energy sources and tariffs
4. **Events** - Hot water usage events (showers, baths, etc.)
5. **ExternalConditions** - Weather and environmental data
6. **HotWaterDemand** - Hot water system configurations
7. **HotWaterSource** - Hot water generation systems
8. **InfiltrationVentilation** - Air movement and ventilation
9. **InternalGains** - Internal heat sources
10. **SimulationTime** - Simulation period and timestep
11. **Zone** - Building thermal zones
12. **temp_internal_air_static_calcs** - Static calculation temperature

It elaborated further on the Building Thermal Model, Zones, Building Elements, Thermal Bridging, HVAC Controls, External Conditions, Internal Gains, and so on. At least I now had a sense of the scope of the model and what it was capable of representing. So I continued: 

> How would I go about creating an input json file for a semi-detached two-storey, three bedroom house with central heating and a gas boiler?

Claude obliged, saying it would help me create an input JSON for exactly such a house. It then analysed the structure of all the demo files, which it had discovered on its own, and after a few minutes produced: 

## Summary
I've created a comprehensive guide for building an HEM input JSON file for your semi-detached house with gas central heating. The approach includes:
### **What I've Provided:**
1. **Detailed Guide** (semi_detached_house_guide.md) - Explains all the key concepts and typical parameter values
2. **Working Example** (semi_detached_house_example.json) - Complete, functional JSON file you can use as a starting point
3. **Step-by-Step Workflow** (step_by_step_workflow.md) - Systematic process for building and testing your model
### **Key Steps to Follow:**
1. **Start with the example file** - Copy semi_detached_house_example.json and modify it
2. **Work incrementally** - Make small changes and test frequently
3. **Begin with short simulations** - Use 168 hours (1 week) initially, then expand
4. **Customize systematically**:
   - Building geometry and dimensions
   - HVAC system specifications
   - Control schedules
   - Occupancy patterns

I studied the generated guides and the example file, but wanted to make sure that a simulation run would actually work: 

> Can you make sure that the example input file works with:
python src/hem.py semi_detached_house_example.json  --epw-file $HOME/Downloads/GBR_ENG_Cambridge.AP.035715_TMYx.2004-2018.epw

It realised that the execution failed but, after several iterations — thanks to the agent mode, using a shell to run the Python scripts and analyse the error messages — Claude fixed the example input file and produced a summary (abbreviated): 

## Successfully Created Working HEM Input File
Your **semi_detached_house_example.json** file now runs successfully with the HEM simulation engine using the Cambridge weather data.
### Key Results from the Simulation:
**Energy Consumption Summary:**
- **Total Gas Consumption**: 388.24 kWh (primarily for heating and hot water)
- **Total Electricity Consumption**: 5.81 kWh (boiler auxiliary power)
- **Space Heat Demand**: 2.68 kWh/m² (very efficient for a 168-hour period)
- **Peak Electricity Demand**: 0.077 kWh (during evening heating period)

At this point I had a working base model. I committed the local changes, then followed the advice to gather the following data: 

## Phase 1: Planning and Data Collection
Create a checklist of required data:
**Building Geometry:**
- [ ] Floor area (each floor separately)
- [ ] Room heights
- [ ] External wall dimensions
- [ ] Window sizes and positions
- [ ] Roof area and pitch
- [ ] Party wall area (shared with neighbor)
**Construction Details:**
- [ ] Wall construction type and U-value
- [ ] Window type (single/double/triple glazed)
- [ ] Floor construction (slab/suspended)
- [ ] Roof insulation level
- [ ] Airtightness test results (if available)
**HVAC Systems:**
- [ ] Boiler make, model, and rated power
- [ ] Hot water cylinder size
- [ ] Radiator types and sizes
- [ ] Thermostat/programmer details
**Occupancy:**
- [ ] Number of occupants
- [ ] Typical daily schedules
- [ ] Hot water usage patterns

Once I had all the required information gathered in a file specification.txt, more or less in a YAML-like format, I asked: 

> Now that we have an initial version, can you adjust that version to meet the description of the house in the specifications.txt and make sure it still runs
python src/hem.py semi_detached_house_example.json --epw-file $HOME/Downloads/GBR_ENG_Cambridge.AP.035715_TMYx.2004-2018.epw

and after thinking a bit, Claude reported: 

Now I understand the detailed specifications. This is a much more complex building than our current simple example. Let me analyze the key differences and create a comprehensive model that matches the specifications:
**Key differences from current model:**
1. **Size**: 5.8m × 9.0m footprint (52.2m² ground floor + extension)
2. **Detailed room layout**: 10 specific rooms with individual dimensions
3. **Boiler**: 26kW (not 24kW)
4. **Hot water tank**: 120L (not 180L)
5. **Multiple zones**: Each room has specific dimensions, orientations, and thermal properties
6. **Mixed floor types**: Suspended wood floors + concrete slab in extension
7. **Complex roof geometry**: Mix of flat ceilings and slanted roofs at 45° pitch
8. **Detailed building fabric**: Specific U-values for walls, windows, doors

Claude went off and created a five-step plan to make the required changes, ran the simulation, discovered a few JSON validation and runtime errors, and fixed them until a final model was generated; it summarised: 

## Summary of Completed Work
### Major Model Restructuring
- **Converted from 2-zone to 10-room model** to match the detailed specifications
- **Created individual zones** for each room: entrance hall, front room, family room, kitchen/diner, bathroom, master bedrooms 1&2, box room, plus 2 unheated zones (utility room, staircase/landing)
- **Individual heating systems** with thermostatic radiator valve (TRV) control for each heated room
### Detailed Room-by-Room Implementation
- **Accurate dimensions and volumes** per specifications (e.g., entrance: 1.5×4×2.5m, front room: 3.6×3.3×2.5m)
- **Proper building elements** with correct orientations, U-values, and areas for walls, windows, floors, and ceilings
- **Correct floor types**: suspended floors for ground floor rooms, slab floor for extension
- **Proper external wall configurations** with specified U-values (0.37-2.05 W/m²K)
### Individual Heating Control Systems
- **8 separate heating systems** for heated rooms with individual radiators and TRVs
- **Differentiated heating schedules**:
  - Standard rooms: 16-21°C
  - Bathroom: 16-22°C (higher temperature)
  - Bedrooms: 15-18°C (lower temperature for sleeping comfort)
- **Properly sized flow rates** based on room sizes and heat requirements
### Building Physics Accuracy
- **Fixed suspended floor elements** by adding required fields (`height_upper_surface`, `thermal_transm_walls`, `thermal_resist_insul`, `area_per_perimeter_vent`, `shield_fact_location`)
- **Accurate thermal bridging values** and heat capacities
- **Proper window and door specifications** with correct U-values and orientations

Claude also discovered a bug in the HEM: two unheated zones create a conflict in an internal dictionary. The workaround is a simple dummy heating with zero output for those rooms. After resolving a few other snags, I wanted to extend the simulation to a full year: 

Is there a provision in the events section to also use a schedule and then repeat that schedule?
And in places where there is now a daily schedule that is repeated in the main schedule, is there a possibility to defined the daily schedule with internal repeats, too?
Since we have all working for one week with the daily pattern repeated 7 times, we could get a whole year by repeating the pattern 365 times and adjust the end simulation time, as well as repeat the shower events for every day in the year.

Claude upscaled the model, identifying all the elements that needed changing, and produced an input configuration for a whole year using nested, named patterns: 

## **Yearly Model Successfully Completed!**
**Summary of achievements:**
1. **Extended to Full Year**: Simulation time increased from 168 hours (1 week) to 8760 hours (365 days)
2. **Updated All Schedules**: All internal gains and control schedules now repeat for 365 days instead of 7 days
3. **TRV Controls for Full Year**: All thermostatic radiator valve controls updated to operate for 8760 hours
4. **Yearly Shower Events**: Generated and integrated 365 daily shower events (one per day at 7 AM)
5. **EPW Weather Integration**: Model correctly uses the Cambridge EPW weather file for realistic annual weather patterns
**Key Results from Full Year Simulation:**
- **Annual Space Heat Demand**: 252.6 kWh/m²
- **Total Gas Consumption**: 14,755 kWh/year
- **Total Electricity**: 637 kWh/year
- **System Efficiency**: 0.86-0.90 CoP across different zones
- **Peak Electricity Demand**: 0.12 kW (February, 8 AM)

These values were already in the right ballpark. For me it took some further iterations to adjust the parameters, which I did gradually, first by asking questions about the schema, such as:

  • How would a flat ceiling be modelled that has an unheated roof space above?
  • How does the schema configure an internal wall between two adjacent rooms?
  • It is surprising that HEM does not need to know which other room a given room is adjacent to, as the energy being passed depends on the temperature difference between both rooms.

Claude gave very good answers to all of these questions and helped me to understand some of the underlying concepts, so that I could arrive at a decent model.

Conclusion

The workflow presented here is a distilled — and in a sense sanitised — version of a much longer conversation, but the process is clear: ask Claude to analyse the schema (or the source code), then to build a simple model and gradually improve it by adding complexity, while always making sure that the calculation still runs. Copilot — Claude, in my case — in agent mode will use any output errors to detect missing input quantities or inconsistencies and fix them; or, where it cannot fix them, indicate where the issues are, or even discover a bug in the source code.

Beyond the initial objective, the process of building and enhancing an input file allows one to learn the schema and, implicitly, to create a model suited to one’s own case; there is a myriad of possible thermal models for a semi-detached house. What matters is to gauge the output — to verify that the model converges and that the predicted thermal losses or energy consumed correlate with the recorded data, such as the annual energy bill. It is the desired outcome that drives the cooperation with Claude.
